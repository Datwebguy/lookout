## Decisions made (most recent first)
- **Autodesk Forma Site Design: not integrating it.** Came up because the user was listening to a real FortyGuard-hackathon-team-hosted webinar segment on it (confirmed via a screenshot showing "Answered by FortyGuard Hackathon Team") and asked if Lookout needed it. It's a legitimate, sanctioned partner tool, but the user confirmed it was presented as an available option, not tied to a bonus track or prize. Forma's actual capability (sun/wind/thermal analysis on a hand-drawn site boundary for architectural design decisions — FAR/GFA/area metrics) is a one-time design-phase tool, structurally different from Lookout's continuous real-time monitoring. Skipping it; FortyGuard's own `satellite_segmentation` (tree canopy / land cover) already covers the one plausible overlap (shade context) if that's ever wanted.
- **Minimal self-serve onboarding, not full accounts.** Directly answers the "how do users set things up" gap the user raised (no signup, no per-user notification config, no login existed before this). Chose the middle of three options I offered (ops-configured+narrate / minimal self-serve / full accounts+login) given ~11 days left before submission — full accounts would be multi-day work competing with hardening time. Built: a real "Add a site" form (name, lat/lon, role, shift, risk flags, notes, optional per-site Slack/Discord webhook) posting to a new `POST /api/sites`, writing straight into `lookout/data/sites.json`. No login layer — the dashboard is still public to anyone with the link, which remains a known, accepted limitation of this scope choice.
- **Verified live (not assumed): non-US coordinates fail cleanly.** Tested a real Toronto, Canada polygon through `area_weighted_mean_temperature` — FortyGuard returned zero tiles, and the code raised `SignalUnavailableError` cleanly with no crash, confirming NFR1 ("handle non-US coordinates cleanly") already holds without needing new code.
- **Demo UI is TWO separate pages (`/` landing, `/app` dashboard), reversing the earlier one-page decision.** Originally built as one combined page (reasoning below, kept for history), but the user reviewed it and said mixing marketing copy with a live operational widget looked unprofessional. Rebuilt as a clean split: landing is pure pitch with zero API calls, `/app` is the real product with zero marketing copy. Trust the user's direct reaction to the actual rendered page over the earlier abstract reasoning.
- **Blue palette, not orange.** User reviewed the orange build and asked to switch. No specific reason given beyond preference — don't re-litigate, this is a settled choice now.
- **No hyphens or dashes anywhere in written copy.** Explicit user request after reviewing the orange build. Applies to all prose I write (headlines, body copy, button labels, status messages) — does NOT apply to real LLM-generated decision text shown in the feed (that's real data; altering it would violate the golden rule) or to CSS/HTML/JS identifiers (kebab-case class names aren't visible copy).
- **Fix "looks stuck" during a live run, don't just leave it.** User tried the app themselves, clicked "Run a live check," and found the page gave no visible feedback while a real ~2 minute cycle ran (site cards/feed just sat there unchanged). Fixed with a dimmed `is-updating` state + spinner on the status message, so the UI visibly acknowledges work is happening instead of looking broken.
- ~~Original one-page reasoning (superseded above): the worker never visits a web page day-to-day since alerts go via Slack; the web UI is for buyers/judges who need pitch + live proof in one continuous scroll, matching the single "Live demo URL" the submission checklist expects.~~
- **Design grounded in real research, not invented blind, for both palette passes.** 2026 SaaS design trend research (WebSearch) informed the general dark-theme-plus-accent-color direction before either color choice; existing real heat-safety apps (OSHA-NIOSH, AIHA) converge on real-time risk level + location-specific projection + actionable guidance as the core UI pattern, which the dashboard already matches regardless of palette. The "typical weather app" comparison card keeps a flat light/paper background on purpose in both versions, to visually code it as the "boring, generic" alternative next to Lookout's real per-site cards.
- **LLM provider = OpenAI (`gpt-5.6-luna`), not Claude/Anthropic.** User preference, changed 2026-08-18 mid-build — not a FortyGuard or technical requirement. `gpt-5.6-luna` chosen specifically for cost ($0.20/$1.20 per 1M tokens vs $5/$30 flagship `gpt-5.6-sol`) per explicit user request; verified pricing and exact model-ID strings live against the OpenAI docs rather than guessing. Real proof cost was a few cents total. Uses the Responses API (`client.responses.create`), not Chat Completions.
- **Signals layer always submits a ~2km bounding query AOI, never the raw site polygon.** Live testing found a real minimum query-area threshold: a small worksite polygon (200m up to 1.5km per side) returns zero tiles even on dates otherwise 100% reliable (confirmed on 2024-07-15 and 2026-08-15, both proven reliable with a larger box); a ~2km box works consistently. `lookout/signals.py` now builds a `_bounding_query_aoi` around the site's centroid for every API call, then area-weights the *result* against the real (smaller) site polygon — this was the actual root cause of what first looked like a live outage.
- **Use a 3-day safety margin for "the most recent available date," not 1 day.** Live testing showed "yesterday" is NOT reliably available — it returned real data multiple times early in a session, then returned empty on an identical retry later, while dates 3+ days old stayed consistently available throughout. `most_recent_available_date()` defaults to `today - 3 days`.
- **Forecast mechanism = historical-analog, not live forecast** (see Open questions below for the evidence). This changes every downstream milestone that touches "ahead"/"forward" signal — always use historical-analog, never attempt to query today's date expecting real-time or near-future data.
- Trust a real API response over even the shipped client's own source-code comments — `fortyguard/client.py` incorrectly documents tcm units as °F; live data proved Celsius.
- Build on the official `fortyguard` Python client, not hand-rolled HTTP.
- Reason on **duration** of danger (exceedance/persistence), not just peak temp.

- Primary track = Agentic (06); secondary = Cities (01), Government (04).
